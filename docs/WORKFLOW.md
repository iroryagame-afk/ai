# CSNPK 跨设备协作流程

本流程让用户、Codex 与网页版助手通过 GitHub 共享任务状态，不依赖聊天之间自动继承上下文。

## 一、信息分层

| 层级 | 唯一职责 |
| --- | --- |
| GitHub Issue | 目标、范围、验收条件、授权范围、当前状态 |
| PR | 页面、代码、图片、数据文件的实际变化及审核讨论 |
| Commit | 可复现的精确版本证据 |
| `tasks/current/issue-<编号>.md` | 数据时点、判断、完成项、阻塞项和继续方法 |
| `docs/*.md` | 跨任务长期有效的规则 |
| 聊天 | 临时沟通，不作为唯一记录 |

## 二、任务生命周期

1. 使用 `.github/ISSUE_TEMPLATE/` 创建任务，填写目标、标的、时间口径、交付物、验收条件和授权范围。
2. 创建 `tasks/current/issue-<编号>.md`，从 `tasks/HANDOFF_TEMPLATE.md` 复制并填写。
3. 从最新远端默认分支建立 `codex/issue-<编号>-<slug>` 独立分支；若当前工作树有并发改动，使用独立 worktree。
4. 重新核验所有会变化的数据。历史聊天、旧截图、旧页面和旧交接只能作为线索。
5. 完成分析、页面、图片和数据文件；记录数据来源、截至时间、证据等级和未核验边界。
6. 执行本地构建、静态检查和范围检查，只提交本任务文件。
7. 若获得授权，推送分支并创建 PR；PR 必须关联 Issue，并列出数据口径和验收状态。
8. 若获得部署授权，从已推送且可识别的 Commit 部署；不得从含未提交改动的工作树直接部署。
9. 使用 cache-busting URL 回读公网 HTML、Markdown、JSON 和图片；必要时比较哈希并完成桌面/移动端视觉检查。
10. 更新 Issue、PR 和任务交接。任务完成后将交接文件移到 `tasks/completed/`。

## 三、权限规则

Issue 中的权限勾选是本任务的执行边界：

- 未授权推送：可在本地完成并给出差异，但不得推送或创建 PR。
- 未授权更新 Issue：提供可复制的 Issue 留言，不得替用户外部写入。
- 未授权部署：最多到 `ready_for_review` 或 `merged`，不得把本地/PR结果描述为上线。
- 未授权修改 Secrets：不得查看、导出、提交或更改凭据和托管配置。
- 任何股票研究、提醒或页面任务均不包含下单授权。

## 四、状态定义

| 状态 | 定义 |
| --- | --- |
| `planned` | 任务合同已建立，尚未执行 |
| `in_progress` | 正在分析或制作 |
| `blocked` | 硬门失败或需要用户决定，线上旧版保持不变 |
| `ready_for_review` | 本地检查完成，等待审核或授权 |
| `merged` | 代码已合并，但不代表已经部署 |
| `deployed_unverified` | 已部署，但公网回读或视觉验收尚未完成 |
| `published_verified` | 已部署并通过规定的公网回读与验收 |

## 五、手机端继续任务的标准指令

只读检查：

> 读取 `iroryagame-afk/ai` 的 Issue #128、对应 Handoff 和最新 PR。重新核验数据时点，告诉我完成、未完成和风险。本次只读，不更新 GitHub，不部署。

继续制作但不部署：

> 继续 Issue #128。允许修改独立分支、推送、创建或更新 PR、更新 Issue；不允许部署和修改 Secrets。

允许上线：

> 继续 Issue #128。核验全部数据门禁和 PR 后允许部署；必须从已推送 Commit 部署，完成公网回读并更新 Issue 与 Handoff。不得修改 Secrets。

## 六、冲突处理

- 用户最新明确指令优先于 Issue；应先把变化更新回 Issue，避免任务合同继续陈旧。
- Issue 只管理本任务，长期规则变更应单独修改 `docs/` 并在 PR 中说明影响范围。
- 同一文件出现其他任务未归属改动时，停止批量暂存；通过独立 worktree 或拆分 PR 处理。
